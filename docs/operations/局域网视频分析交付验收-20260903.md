# 局域网视频分析交付验收

检查日期：2026-09-03。

用户确认的交付场景：5～10 台电脑同时使用，单条视频在 30 分钟以内，主要提交抖音链接。

## 当前结论

先冻结新功能，把本次修复作为候选交付版本。完成真实主机安装、多人登录和真实视频连续分析验收后，再正式交付。

当前实现是多浏览器向同一主机提交任务，Python Worker 逐条分析。视频内部的语音、画面处理有并行执行，但启动脚本没有启动 10 个独立的视频 Worker。因此不能把“10 人同时提交”承诺为“10 条视频同时计算”。等待时间需要按真实样片测量；队列测试不代表处理吞吐量达标。

## 已修复并验证的问题

| 问题 | 原先的表现 | 本次处理 |
| --- | --- | --- |
| 多人同时提交相同链接或文件 | 前置查重均通过，后续唯一约束冲突返回 500 | 保留数据库防重与事务回滚，返回明确的 409 和刷新、复用指引；上传失败仅清理该请求的独立媒体对象 |
| 中断后的自动恢复 | 接回旧任务仍保留原来的高进度，新的下载或分析心跳被判定为进度回退 | 每次领取重建当前运行状态，普通任务从队列起点开始，有检查点的任务从恢复进度开始；旧 Worker 的版本和租约仍无效 |
| 跨项目队列展示 | 只统计当前项目，忽略其他电脑在其他项目提交的工作 | 展示主机共享队列的等待和处理数量；其他项目只返回汇总数量，不返回任务内容 |
| 排队时间估算 | 将等待时间算进单条处理时间，再推算剩余时间 | 基线采用首次领取到完成的处理时间，排除重试样本；页面显示参考处理耗时，不给出虚假的完成倒计时 |
| 分析结束瞬间被取消 | 提交结果收到 409，退出整个共享 Worker | 放弃该任务的过期结果，继续处理其他任务 |
| 保存报告时响应丢失 | 分析结果没有立即重传，可能等租约到期后重新计算 | 使用相同结果键重传，最多 3 次；保留服务端幂等校验和认证失败处理 |
| 单个来源损坏 | 领取失败可能导致整个 Worker 重启；损坏的人工转写可能被反复领取 | 服务端将损坏转写标为失败，Worker 跳过已明确失败的来源任务 |
| 多人同时重新分析 | 每个人都通过查询检查，各自建立新任务 | 数据库写入时原子检查是否已有活动任务，只建立一个任务及其审计记录 |
| 旧任务与新分析竞争 | 旧失败任务可再次排队，与新分析同时运行 | 重试核对读取时的版本，并在写入时排除同视频的其他活动任务；清空上一轮完成时间 |

跨项目同时首次提交相同素材时，竞争失败方会收到 409；再次提交可进入原有的公司素材库复用流程。本次没有把失败响应伪装成成功。

## 正式交付前必须完成的真机验收

使用独立验收公司和项目，在候选交付包上测试，保存每条任务 ID、提交时间、开始时间、结束时间和结果。下表均为待完成项目。

| 场景 | 操作 | 通过标准 |
| --- | --- | --- |
| 主机首次安装 | 在目标主机执行 `setup-local.bat`，按需执行 `tools/setup-analyzer.bat`，再启动 `start-lan.bat` | Python 3.11、FFmpeg、ASR/OCR、模型配置就绪；网页显示分析服务在线；至少 1 条真实样片完成 |
| 10 人同时提交 | 10 个独立账号、浏览器分别提交授权可分析的不同抖音链接，覆盖短片、约 10 分钟、接近 30 分钟的视频 | 任务全部登记；没有重复或遗漏；每个账号仅能进行被授权的操作；记录真实等待时间和处理时间 |
| 重复和竞争操作 | 同时提交同一链接；多人同时点重新分析；旧失败任务与新分析竞争 | 只有一个有效新任务；失败方收到可理解的说明；不重复计算、不覆盖其他任务结果 |
| 页面离开 | 提交后刷新、关闭页面，再登录查看 | 主机继续处理；重新进入能看到正确进度和结果 |
| Cookie 失效 | 在验收环境使用失效快照，再导入有效的抖音 Cookie 并重试 | 明确提示下载或登录问题；更新后可恢复；其他视频任务不因此停止 |
| 用户取消 | 在下载、分析和结束阶段分别取消其中一条 | 被取消任务不能写入最终报告；其他人的队列继续；记录底层操作实际停止所需时间 |
| 主机或服务重启 | 在中间处理阶段和保存检查点后分别中断服务，再启动 | 旧运行不能再提交；租约到期后可恢复任务；检查点恢复不因进度回退失败 |
| 网络故障 | 临时断开外网或使模型服务不可用后恢复 | 错误可定位，恢复方式清晰；不把失败当成功；其他任务可继续处理 |
| 连续运行 | 10 个账号累计提交至少 30 条真实视频，覆盖半天使用过程 | 主机无崩溃或长期离线，内存和磁盘可接受，未完成任务都有原因和恢复办法 |
| 客户交付包 | 用 `prepare-delivery.bat` 重新生成包，在独立路径安装验收 | 包中包含修复，安装和局域网入口有效，不带开发数据库、Cookie 和模型密钥 |

测试线程数量不等于实际电脑数量。必须由真实浏览器登录、通过局域网地址完成多人测试，特别核查邀请、会话、项目访问、共享素材与取消权限。

## 性能与上线安排

先测出不同长度视频在目标主机上的实际处理耗时。单 Worker 下，10 人各提交一条视频，队尾等待约等于前面任务处理时间之和。按长短片分别记录，不能仅用视频时长或单条最快成绩承诺等待时间。

如果这个等待时间业务上不能接受，需要另行设计受限的多 Worker 部署，并验证主机内存、ASR/OCR 模型占用、外部模型限流和抖音 Cookie 的稳定性。不能直接把并发数改成 10：当前流水线存在复用的模型实例和分段检查点回调，需要明确每个 Worker 的进程和状态边界。

通过以上验收后，先让 2～3 人试用一个工作日，再扩大到 10 人。交付时写明支持的使用规模、主机在线要求、排队方式、Cookie 更新操作和备份恢复步骤。
