# 抖音下载间歇失败排查

## 客户反馈与证据

客户截图中的失败发生在 5% 获取媒体阶段，显示“本地浏览器登录态和备用 Cookie 都无法使用”。用户补充：后面的任务完成后，回来点击重试就成功，期间没有提到更换 Cookie。

这不足以证明 Cookie 过期。临时网络失败、抖音访问限制、浏览器 Cookie 读取失败和错误归类不准确都需要区分。

已检查用户提供的 `analyzer.log`，大小 92,309 字节：

- 有 85 条 `[download] 100%` 记录，表示下载完成记录数量，不等于 85 条视频已完成全部分析。
- 有 13 次 `funasr version: 1.4.1.` 输出，单凭这些记录不能确定是否发生进程崩溃或重启。
- 没有任务 ID、按行时间戳或可定位此次失败的错误堆栈。
- 因此，无法从这份正常输出日志将失败与后续重试成功对应起来。

随后收到并检查客户 `analyzer-error.log`（3,335,720 字节）和 `analyzer-supervisor.log`（2,542 字节）。无需再索取这些文件，也无需发送 Cookie 文件或 `.dev.vars`。

## 本地代码中确认的问题

1. 已安装分析包仍包含截图中的旧文案和优先读取浏览器的逻辑。原启动脚本从项目根目录执行 `python -m liming_analyzer`，可能加载 `site-packages` 中的旧副本，导致修改源码后修复未生效。这是本地复现的版本问题，尚未确认客户环境使用相同版本。
2. 远程组织 Cookie 快照与手工导入 Cookie 共用目标路径；远程快照不存在时，客户端会删除该路径。由此可能删掉手工导入文件，或者让不同组织的任务覆盖同一份文件。
3. yt-dlp 会在关闭时保存 Cookie jar，直接把共享文件交给它可能改写原快照。
4. 下载器的抖音提取器在非致命详情请求失败、没有返回详情时，会抛出 `Fresh cookies (not necessarily logged in) are needed`。这句错误并不证明登录已失效。
5. 原解析逻辑会在任意下载异常后切换至浏览器登录态，最后一个 Cookie 读取异常可能覆盖先前的超时或网络异常。

## 本次修复

- 两条 Windows 分析启动路径都优先加载当前交付目录中的源码，并在监督日志中记录来源目录。
- 公司 Cookie 快照放入每次任务独立的临时目录，未上传时保留主机手工导入文件；不依赖配置一个本地 Cookie 路径才能使用网页上传的快照。
- 给 yt-dlp 提供独立可写副本，退出后清理，避免覆盖原文件或其他任务。
- 保留下载器非致命警告中的具体错误类别，避免被后续通用 Cookie 提示覆盖。
- 网络异常、平台限流、访问校验、浏览器 Cookie 读取失败、Cookie 格式问题分别编码并给出对应指引。
- 对明确的网络超时或服务端暂时异常，额外等待 3 秒重试一次；限流、访问校验错误不进行密集自动重试。
- 任务日志增加时间、任务 ID 和错误类别；不记录 Cookie 内容或带敏感参数的原始请求。
- 后台浏览器登录检测不再反复输出下载器的原始错误；仍向网页返回真实检测状态，只在状态变化时记录明确的 `Browser probe state changed` 日志。视频任务失败记录保持独立，不将登录检测失败伪装成正常。
- 旧版 `DOUYIN_COOKIE_EXPIRED` 记录的页面指引改为先稍后重试，持续失败时再核对视频和更新 Cookie。
