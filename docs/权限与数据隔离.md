# 权限与数据隔离基线

## 信任边界

浏览器提交的 `organization_id`、`project_id` 和角色都不可信。服务端必须先从认证身份查出有效公司成员关系，再查项目成员关系，最后把可信范围注入查询。

```text
认证用户
→ 有效 organization_members
→ 有效 project_members（公司管理员除外）
→ 查询同时限定 organization_id + project_id
→ 写操作记录 actor、目标和时间
```

## 第一版固定角色

| 层级 | 角色 | 主要权限 |
|---|---|---|
| 公司 | admin | 公司设置、成员、全部客户项目 |
| 公司 | member | 仅进入已分配项目 |
| 公司 | readonly | 仅查看已分配项目 |
| 项目 | owner | 项目配置、成员与完整内容流程 |
| 项目 | planner | 分析、策略、选题和文案 |
| 项目 | creator | 内容与素材生产 |
| 项目 | reviewer | 内部审核与评论 |
| 项目 | client | 客户审核与评论 |
| 项目 | readonly | 项目只读 |

## 强制规则

- 跨公司访问直接拒绝，不返回目标是否存在。
- 非公司管理员必须具有有效项目成员关系。
- 公司只读和项目只读都不能写。
- 客户成员可以审核，不得访问内部模型配置、成本和其他客户数据。
- 成员移除使用状态停用，历史审计记录保留。
- 邀请只保存令牌哈希，必须有过期时间且一次性使用。
- 媒体对象键使用 `organizations/{organization_id}/projects/{project_id}/...` 前缀。
- 重要更新带版本号；长任务使用组织范围内唯一的幂等键。
- 物理删除由异步任务执行，并写入审计日志。
