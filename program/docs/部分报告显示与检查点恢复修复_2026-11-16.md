# 部分报告显示与检查点恢复

## 原机证据与首因

用户导出的 `analysis.v12` 报告为纯视觉、省时档，视频 434 秒，采样 35 张；全部画面最终取得有效结果，本地 OCR 调用为 0。选题、画面、综合三个模块完成，共 9 条结论，只有文案、价值与行动模块以 `length` 失败。

文案模块实际首请求输出上限为 6000 tokens，模型以 `finish_reason=length` 结束，记录的思考 token 为 2418。当前兼容层已设置模型支持的低思考强度，并不是漏配；本轮没有修改模型参数或用户 Token 上限。

显示失败的首因是文案失败元数据为 `validation={passed:false,issues:[]}`。TS 校验要求验收状态与问题列表一致，因而拒绝整个结构化分析。统一报告随后拿不到证据注册表，级联产生缺证据、引用无效、口播范围不一致等错误；原始报告的 346 条证据和引用实际可以通过校验。

同一误判还使模块检查点恢复不可用。列表和详情原本把操作错误放在页面顶部，滚动后按钮处看不到反馈，表现为点击“从检查点继续”没有反应。

## 修复行为

1. Python 生成失败结果时，空 SDK 问题数组回退为已有的安全失败原因，防止新报告继续出现上述矛盾。
2. TS 仅对解析副本中的历史 `failed + passed=false + 空 issues + 已识别失败原因` 补诊断码。原始报告、正文、引用和状态不改；未知失败原因、错误通过状态、证据缺失、重复引用、缺视觉依据及范围损坏仍拒绝。
3. 已保存的同类旧报告无需重新采集或调用模型即可恢复有效部分的展示。本次客户 JSON 原样复验后，内容与统一报告均有效，三个完成模块恢复显示，文案模块仍如实标记未完成。
4. 检查点继续沿用现有模式、档位和来源，定向恢复失败文案模块。成功的独立模块和原取证保留；文案变化影响综合输入时更新综合判断，输入未变才复用旧综合结果。
5. 明确截断且已到硬上限时，内容模块可以在原两次调用预算中使用第二次同上限请求，定向生成精简但完整的 JSON。分类索引、事实和必要来源仍须保留，截断候选不予验收；仍失败时明确保留失败状态，不无限重试。预算估算同步计入该恢复机会。
6. 列表任务行和详情模块旁显示提交中、已受理或实际拒绝/网络状态，并防止重复提交。受理后列表刷新失败会明确提示，不冒称推理已开始；有效部分报告显示当前实际待补模块，不再把历史级联错误当作当前摘要。

## 验证边界

- 客户原始 JSON 只读复验：346 条证据保持，三个完成模块的 9 条结论可见，输入正文与引用完全未变。附件原文不进入仓库。
- 真实 SQLite 重试接口：历史矛盾元数据经窄兼容后，请求成功，目标仅为失败文案；任务仍为原纯视觉/省时档，取证与成功缓存保留，存储的原报告不变。
- 匿名契约负例继续拒绝真实证据与引用损坏。截断恢复覆盖同上限成功、再次截断、格式修复与长度恢复共用两次预算、配置上限、用量留痕及旧来源签名缓存。
- 浏览器验证使用合成 API，不向客户任务发送恢复请求。客户原机的文案实际补全仍需升级后点击恢复验收。

最终本机回归：分析器 1353 项通过、17 项跳过、163 个子测试通过；Node 全量 1723 项通过、38 项跳过，最终定向组合 108 项通过。类型检查、生产构建与相关静态检查通过。Chrome 合成 API 9 场景通过，包括旧报告展示、检查点受理、409、网络中断、受理后刷新失败及手机反馈。

## 同次记录的性能现象

35 张图中有 7 次初始视觉请求在约 120 秒后报 `MCPError: Request 'tools/call' timed out`，经缺帧恢复后全部完成。抽帧 11.937 秒、筛选 0.563 秒，画面理解墙钟 690.281 秒；串行缺帧恢复的 107.016 秒已包含其中。成功请求平均 10.031 秒，不能把并行请求耗时直接相加。该记录单独保留，不能因最终恢复成功抹掉失败，也不能将它与报告显示首因混为一谈。现有记录能确认工具调用超时，尚不能确定是模型服务还是调用链路。本轮没有据此更改视觉模型、超时或并发。
