### 综合判断与建议未输出：模板标签协议不一致

用户提供的另一份 `analysis.v12` 原机导出显示：视频 220 秒、最高档，任务最终为 `partial`。选题、结构与人群，文案、价值与行动，画面与镜头三个模块均已完成；只有综合判断失败，展示结论数组为空。

- 综合模块两次模型请求分别耗时 2797、2859 毫秒，均以 `finish_reason=stop` 正常返回；输出分别为 441、405 tokens，单次预算 4500。没有记录网络错误、超时或输出截断，不能归因于未配置模型或预算不足。
- 最终校验记录为 `synthesis:compact_untyped_segment_has_tags` 和 `synthesis:schema_invalid`。综合模块输入的来源覆盖为完整，包含 51 条证据，不是前三个模块失败或本模块材料未取得。
- `content_module_protocol.py` 中综合模块唯一的事件种类是 `content_template`（可复用内容模板），没有关联标签维度，因此解码器要求其 `t` 为 `[]`；只要出现非空标签，就抛出上述错误。
- SDK 响应模型却对该字段使用与其他事件相同的 `list[int]`，最多 24 项，允许非空标签通过第一层检查。生成提示仅要求从对应标签表取索引，没有明确说明空标签表必须返回 `t=[]`；通用修复提示也没有解释这条具体规则。模型正常返回不等于已通过业务协议校验。
- 离线合成复现：其余响应完全相同，模板 `t=[]` 时综合模块完成；改为 `t=[0]` 时 SDK 接受，最终解码拒绝，初次调用及自动修复各一次后仍以相同错误失败。此验证没有访问模型服务，也不代表已取得客户两次完整原始响应。
- 导出只包含最终校验错误、用量和状态，不包含失败候选正文。因此可以确认最终失败触发的规则，但不能从此文件确定两次响应分别填了什么标签、哪一条结论是否本可保留。

处理方向：先统一 SDK、提示和最终校验对模板空标签的定义，为这类错误提供明确修复指令；如增加局部规范化，必须保持正文和来源不变、重新执行完整校验并记录恢复行为，不能直接绕过格式或证据检查。随后用相同合成错误验证，再用原机报告补验。

当前任务保留 `evidence_ready` 检查点。现有报告页支持在失败模块内点击“只补这一部分”；服务核对检查点和来源签名一致后，可复用取证及成功模块，仅重试综合判断。该入口可避免整片重跑，但在协议问题修复前仍可能遇到同类失败。本次没有替用户触发收费请求或重新分析。

## 设置里的最终入口

1. **打开页面／自动刷新**：读取上次验证和文件元信息，不运行 GPU 转写，不下载安装。
2. **重新检查**：重新加载基础依赖；适用时以独立、限时子进程运行现有中文样本，显式 CUDA、仅本地模型、不允许自动 CPU 回退。服务运行中或无法确认停服时不抢占显存，显示本次未执行的原因。
3. **一键配置环境并启动**：按平台/设备准备缺失依赖；Windows NVIDIA 首次运行库归档合计约 541 MiB，来源为 NVIDIA 官方固定版本与 SHA-256，不修改 torch、驱动或系统 PATH。随后验证样本，再显示实际结果。
4. **正式分析**：使用相同受校验的项目运行库与加载模块。`auto` 出错保留 CPU 回退和真实原因；明确 `cuda` 保持严格语义，不悄悄改成 CPU。
