# 采集稳定性与画面档位

## 采集与连续任务

用户反馈 Windows 链接采集反复出现 `errno=22`，并补充等待约五分钟后重试可成功。提供的错误栈指向旧 `browser_capture.py:947` 的关流语句；该循环先关 stdin，再关 stdout，错误栈本身不能确定哪条流失败，也不能证明所有失败任务原本已取得完整媒体。

代码及故障注入确认了两处问题：

1. 清理段中关流异常会覆盖采集返回值或原 AppError，同时跳过剩余回收。现已改为逐项、有总时限的清理，先阻断晚到写入，确认 reader 已退出才关 stdout；单项清理失败不会覆盖原业务结果。日志仅包含固定动作、流名、异常类型和 errno。
2. 失败状态原本只上报一次。若请求在服务端写入前暂时中断，旧租约可能保留到 300 秒上限。现与完成收据一样，以同一结果键有限重试失败收据，最多三次、间隔 1 和 2 秒，不重新执行采集或模型，也不放宽租约权限。五分钟现象与此机制接近，但尚无原机证据确认那次确实发生了上报中断。

正常完成的任务继续复用已加载模型。清理失败、超时或浏览器退出未确认时，当前结果可以保留，但隔离父进程必须先回收旧处理子进程及其后代，再接受下一条。Node 驱动明确回传浏览器关闭是否成功，关闭等待仍有五秒上限。无法确认进程已经退出时，继续沿用拒绝启动下一任务的安全边界。

故障注入已覆盖成功、业务失败、取消、超时、stdin/stdout 关闭错误、读线程不退出、写回调在途和日志异常。原生子进程测试验证异常清理后当前结果保留、下一条改用新 PID，后续健康任务重新复用；SQLite 接口验证未写入／已写入但丢 ACK 两种失败上报均可恢复领取下一条。没有以故障注入代替 Windows 原机发生机制验证。

## 30 分钟任务的短暂超时

2026-11-16 18:10:29 本机开始任务 `2f05dfca-7a62-4a18-b505-11aa446ce510`。采集耗时 156.1 秒、媒体准备 77.8 秒，18:14:26.975 进入原片保存阶段，约 3.4 秒后报 `WORKER_PROCESSING_FAILED: timed out`。数据库没有该任务的原片资产、转写检查点或模型调用。记录支持“已完成采集、保存阶段失败”，不支持“30 分钟触发采集上限”。原片上传请求原有 30 秒连接等待、保存阶段 600 秒时限，都与本次约 3 秒不符；原日志未保留异常来源，不能据此锁定某一个请求。

本机合成故障和 localhost 慢响应复现了控制 GET 等待 2 秒后直接结束整条任务的路径，行为与该报错及时间尺度接近。现仅在最近成功响应明确确认同一 attempt 与有效租约时，容忍一次短暂断联并继续检查，恢复期限不超过最近确认后 8 秒，且止于租约到期前 2 秒。初次未确认、旧响应缺少确认字段、明确撤权或取消均不进入恢复。断联时已收到的结果先暂存，重新确认后才交付；租约不续期，所有处理预算和资源回收仍有效。

控制、心跳与原片保存分别输出固定错误码及异常类型，不记录请求凭据。原片保存连接等待调整为 120 秒，处理阶段仍有 600 秒上限，上传异常不自动重放；进入保存前立即更新任务进度。合成验证只证明可复现路径及修复行为，原视频仍需重试验收，不能将它表述为已证实的原机首因或已完成分析。

### 后续重试确认的上传调度问题

同一任务第三次执行开始于 20:26:19。20:30:24.929 完成采集，20:31:42.447 完成媒体准备并进入原片保存；20:31:45.086、20:31:49.101 明确记录 `operation=control` 的 `TimeoutError`，20:31:49.152 以 `ANALYZER_CONTROL_UNAVAILABLE` 停止。该次记录已能确认控制检查连续超时，而非模型分析或采集时长限制；原片保存尚未形成资产或检查点。

隔离 Miniflare、原生 R2/D1 和真实 HTTP 上传复现了阻塞：512 MiB 上传耗时约 8.6 秒，上传期间普通 GET 与 D1 控制请求各 85 次均未进入处理器并触发 2 秒超时。只计算哈希也出现等待，因此不是 D1 锁或 Python 共享连接。上传链连续消费已经就绪的读取、哈希和写入微任务，未给其它请求的事件调度留出机会。逐块加入真实事件循环让出后，实验中的 111 次 D1 控制和 111 次普通 GET 都在上传过程中返回，最大延迟约 9 毫秒；这组数字来自修复方案对照，最终实现的验收另行记录。

正式修复按最多 64 KiB 输出块，每累计 1 MiB 或 64 次操作主动让出事件循环，并复查取消状态。原请求中断会传递到 reader、pump、固定长度流与 R2 写入；保存失败不发布资产，已提交收据及已有原片仍受原接口的租约、幂等和绑定保护。没有扩大控制恢复期限来掩盖上传阻塞，也没有修改用户原视频或重新调用模型。

正式实现的原生真实 HTTP 验收：512 MiB 合成源上传约 9.1 秒，控制和 D1 心跳各 82 次在 helper 结束前返回，最大约 25 毫秒；精确 1 GiB 上传约 18.0 秒，控制 160 次、心跳 161 次在 helper 结束前返回，最大约 55 毫秒，均无超时，R2 字节数与 SHA-256 完全一致。测试使用临时独立 D1/R2，完成后清理，未操作生产媒体。Node 全量回归 1792 passed、38 skipped，另验证 EOF 至 R2 回执期间取消不会返回保存收据，提交后的断连仍保留有效对象。类型检查、生产构建、相关 ESLint 通过；本机工作台健康检查正常，失败任务未自动重跑、模型调用仍为 0。

档位独立于隐藏的旧文字预算设置。档位写入任务、检查点、报告及诊断 JSON；重试保持原档位，重新分析可切换。`0054_analysis_visual_sampling.sql` 的历史默认值为 NULL，旧任务仍按原采样策略恢复，显示“历史采样”，不会误用新档位缓存；旧报告重新分析默认均衡。
